# Microsoft Fabric CI/CD with Azure DevOps

A lightweight, reusable CI/CD framework for deploying Microsoft Fabric items from a Git repository to Fabric workspaces using Azure DevOps pipelines and the [`fabric-cicd`](https://microsoft.github.io/fabric-cicd/latest/) Python library.

Note - this is intented as a sample framework that can be customized to fit your specific scenario for deployments.

---

## Overview

This framework automates the deployment of all Fabric items (Notebooks, Pipelines, Semantic Models, Lakehouses, and more) from a source-controlled repository to target Fabric workspaces. It supports two environments out of the box — **PPE/UAT** and **PROD** — each driven by a dedicated Azure DevOps pipeline.

```
┌─────────────────────────────────────────────────────────┐
│                     Git Repository                      │
│                                                         │
│   ppe branch  ──────────────►  PPE/UAT Workspace        │
│   main branch ──────────────►  PROD Workspace           │
└─────────────────────────────────────────────────────────┘
```

Every push to the `ppe` or `main` branch that touches the Fabric items folder triggers the corresponding pipeline, which publishes the full workspace state from the repository.

## Repository Structure

```
your-repo/
├── .scripts/
│   └── publish_to_fabric.py       # Core deployment script
├── .pipelines/
│   ├── deploy-ppe.yaml            # Azure DevOps pipeline — PPE/UAT
│   └── deploy-prod.yaml           # Azure DevOps pipeline — PROD
└── fabric/
    └── workspace/                 # Root folder for Fabric items
        ├── MyNotebook.Notebook/
        ├── SalesPipeline.DataPipeline/
        └── InventoryModel.SemanticModel/
```

> **Note:** Fabric items follow the `ItemName.ItemType` folder convention as generated by Fabric's native Git integration.

## Prerequisites

### 1. Azure Service Principal

Create a service principal in Azure Active Directory that has **Member** access to both your PPE and PROD Fabric workspaces.

```bash
az ad sp create-for-rbac --name "fabric-cicd-deploy"
```

Note the `appId` (client ID), `password` (client secret), and `tenant` (tenant ID) from the output.

### 2. Azure DevOps Variable Group

Create a variable group named **`vg_fabric_cicd`** in Azure DevOps under **Pipelines > Library > Variable Groups**.

Add the following variables (mark secrets as secret 🔒):

| Variable | Description | Secret |
|---|---|---|
| `FABRIC_TENANT_ID` | Azure AD tenant ID | No |
| `FABRIC_CLIENT_ID` | Service principal client ID | No |
| `FABRIC_CLIENT_SECRET` | Service principal client secret | 🔒 Yes |
| `PPE_WORKSPACE_ID` | GUID of the PPE/UAT Fabric workspace | No |
| `PPE_WORKSPACE_NAME` | Display name of the PPE/UAT workspace | No |
| `PROD_WORKSPACE_ID` | GUID of the PROD Fabric workspace | No |
| `PROD_WORKSPACE_NAME` | Display name of the PROD workspace | No |

> Workspace IDs can be found in the Fabric portal URL when viewing a workspace:
> `https://app.fabric.microsoft.com/groups/<workspace-id>/...`

### 3. Python Dependencies

The deployment script requires two Python packages, installed automatically by the pipeline:

```
fabric-cicd
azure-identity
```

## How It Works

### Pipeline Flow

Each pipeline run executes the following steps:

```
1. Checkout      → Clone the repo with full history
2. Python setup  → Pin Python 3.12
3. pip cache     → Restore cached packages for faster installs
4. Install deps  → pip install fabric-cicd azure-identity
5. Deploy        → Run publish_to_fabric.py
6. Summarize     → Upload summary.md to the ADO pipeline summary tab
7. Artifacts     → Save deployed-items.json + summary.md for download
```

### Authentication

Authentication is handled by `DefaultAzureCredential` from the `azure-identity` library. In a pipeline context it automatically uses the three `AZURE_*` environment variables (passed securely from the variable group) to authenticate as the service principal — no credentials are ever hardcoded.

For local runs, `DefaultAzureCredential` falls back to your active `az login` session.

### Deployment Behaviour

- **Full deployment every time** — the entire repository state is pushed on each run. There is no incremental/diff-based deployment.
- **All item types** — `item_type_in_scope` is omitted, so the library defaults to deploying every supported Fabric item type it finds in the repository directory.
- **Orphan cleanup** — after publishing, `unpublish_all_orphan_items` removes any items that exist in the workspace but are no longer present in the repository (i.e. items deleted from source control). Set `--SkipUnpublish "true"` to disable this.

### Output Artifacts

Each pipeline run produces two artifacts saved to the `deployed-items-ppe` or `deployed-items-prod` artifact container:

| File | Description |
|---|---|
| `deployed-items.json` | Machine-readable list of every item deployed, including workspace ID, workspace name, item name, and item type |
| `summary.md` | Human-readable deployment summary surfaced in the ADO pipeline Summary tab, grouped by item type |

## Setup Instructions

### Step 1 — Add pipelines to Azure DevOps

1. In your Azure DevOps project, go to **Pipelines > New Pipeline**
2. Select your repository and choose **Existing Azure Pipelines YAML file**
3. Point to `.pipelines/deploy-ppe.yaml` and save
4. Repeat for `.pipelines/deploy-prod.yaml`

### Step 2 — Update paths

In both YAML files, update the two path references to match your repository layout:

```yaml
# The branch path filter — folder containing your Fabric items
paths:
  include:
    - fabric/workspace/**   # ← update this

# The RepoDir variable — same folder, prefixed with the ADO sources directory
variables:
  - name: RepoDir
    value: '$(Build.SourcesDirectory)/fabric/workspace/'   # ← update this
```

Also update the `scriptPath` in the deploy step if you place `publish_to_fabric.py` somewhere other than `.scripts/`:

```yaml
scriptPath: '$(Build.SourcesDirectory)/.scripts/publish_to_fabric.py'   # ← update if needed
```

### Step 3 — Link the variable group

Ensure both pipelines have access to the `vg_fabric_cicd` variable group:
- Go to **Pipelines > Library > vg_fabric_cicd**
- Under **Pipeline permissions**, add both pipelines

### Step 4 — Trigger a deployment

Push a change to the `ppe` or `main` branch (touching a file inside your Fabric items folder) and the corresponding pipeline will trigger automatically.

## Local Deployment

You can run the deployment script locally for testing:

```bash
# 1. Authenticate
az login

# 2. Install dependencies
pip install fabric-cicd azure-identity

# 3. Run
python .scripts/publish_to_fabric.py \
  --WorkspaceId      "<your-workspace-guid>" \
  --WorkspaceName    "<your-workspace-name>" \
  --Environment      "PPE" \
  --RepositoryDirectory "./fabric/workspace/" \
  --OutputJsonPath   "./deployed/deployed-items.json" \
  --SkipUnpublish    "false"
```

## Customisation

| Goal | What to change |
|---|---|
| Add a new environment (e.g. DEV) | Copy `deploy-ppe.yaml`, update branch trigger, variable names, and stage name |
| Deploy only specific item types | Pass `item_type_in_scope=[...]` explicitly in `publish_to_fabric.py` |
| Skip orphan cleanup | Set `--SkipUnpublish "true"` in the pipeline arguments |
| Use a different Python version | Update `versionSpec` in both YAML files |
| Use parameter substitution across environments | Add a `parameter.yml` file to your workspace folder — see the [fabric-cicd parameterization docs](https://microsoft.github.io/fabric-cicd/latest/how_to/parameterization/) |
